# Решения и допущения

## Уточнения к ТЗ

1. Удаление задачи удаляет её историю.
2. Удаление объекта удаляет его задачи вместе с историей.
3. Постановщик правит задачу в любом статусе, кроме «Принята». Смена исполнителя возвращает задачу в «Новая».
4. Исполнитель у задачи обязателен.
5. Принять задачу или вернуть её на доработку может любой постановщик, не только автор.
6. Объекты правит любой постановщик.
7. Правки полей задачи тоже пишутся в историю.

## Решения

### Данные и правила

- **Статусы и переходы — справочники в базе.** `task_statuses` хранит название, порядок и признак финального статуса. `task_transitions` хранит допустимые переходы: кто их выполняет, нужен ли комментарий, текст кнопки. По этим таблицам работают и функция смены статуса, и интерфейс. Новый статус или переход добавляется строками в таблицы, без правки кода.
- **Статус меняется только через функцию `change_task_status`.** Прямая запись в колонку статуса запрещена правами.
- **Исполнителем назначается только пользователь с ролью «исполнитель».** Постановщик задачи не выполняет.
- **«Принята» — финальный статус.** Из него нет переходов, задачу нельзя править. Удалить принятую задачу постановщик может: это согласуется с тем, что при удалении объекта удаляются и принятые задачи.
- **Комментарий можно оставить при любой смене статуса.** Обязателен он только при возврате на доработку.
- **История хранит имена, а не ссылки.** Для объекта и исполнителя в правках записываются имена на момент правки. Так история читается, даже если у читателя нет доступа к прежнему объекту или пользователь удалён.
- **Автора задачи подставляет база** (текущий пользователь), подделать его нельзя.

### Доступ

- **Исполнитель видит имена всех пользователей**, иначе история была бы нечитаемой. Email в профилях не хранится, поэтому чужие адреса не видны. Пользователь, созданный без имени, получает имя «Новый пользователь».
- **Чужая задача для исполнителя не существует.** API отвечает «Задача не найдена», интерфейс — «не найдена или у вас нет к ней доступа». По ответу нельзя понять, есть ли такая задача.
- **Регистрации и управления пользователями нет.** Пользователей создаёт `scripts/seed.ts` или администратор в панели Supabase. Роль постановщика выдаётся только SQL-запросом или секретным ключом.

### Интерфейс

- **«Мои задачи»:** исполнителю — назначенные ему, постановщику — поставленные им. На странице есть пояснение, что принять можно любую задачу.
- **Стартовая страница:** исполнитель после входа попадает в «Мои задачи», постановщик — в «Объекты».
- **Кнопки только доступных действий.** Права всё равно перепроверяет база.
- **Подтверждение** нужно перед переходом в финальный статус и перед удалением.
- **Интерфейс на русском, без пагинации и realtime.** Данные обновляются при переходах по страницам и после действий.

### Инфраструктура

- **Без отдельного бэкенда.** Проверки — в Postgres (RLS, права на колонки, функция, триггеры), фронт статический.
- **`npm run dev` и тесты работают с локальным Supabase** и облако не трогают. Тесты дополнительно отказываются запускаться не на локальной базе.
- **Пароль демо-пользователей не хранится в репозитории.**

## Допущения и ограничения

- **Время в истории** берётся с часов сервера и показывается в часовом поясе браузера. Демо-история создана скриптом за пару секунд, поэтому время у событий почти одинаковое.
- **Одновременная смена статуса.** Функция блокирует строку задачи. Второй запрос увидит уже новый статус и получит отказ, если переход из него невозможен.
- **Перезапуск seed** пересоздаёт демо-пользователей. Тех, кто был в системе, вернёт на страницу входа.
- **Нет восстановления пароля, уведомлений, фильтров и поиска**: в ТЗ их нет, а почта в проекте не настроена.
