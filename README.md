# Мини-CRM «Объекты и задачи»

Тестовое задание 2b-studio: постановщик заводит объекты и задачи, исполнитель ведёт их по статусам, каждая смена статуса попадает в историю.

- **Приложение:** https://2b-studio-mini-crm.vercel.app
- **Коротко для руководителя:** [EXPLANATION.md](EXPLANATION.md)
- **Решения и допущения:** [DECISIONS.md](DECISIONS.md)

| `executor2@crm.test` | Сергей Кузнецов | исполнитель |

Пароль у всех один, он передан в сопроводительном письме.

В демо 3 объекта и 7 задач во всех статусах, у двух задач есть возврат на доработку с комментарием. «Склад в Химках» есть только у Сергея, поэтому Иван этот объект не видит. Если демо-данные испортились, `npm run seed -- --cloud` пересоздаёт их с нуля.

## Стек

React 19, TypeScript, Vite, Mantine, react-router. Данные, вход и API — Supabase (Postgres, Auth, PostgREST). Хостинг фронта — Vercel.

Отдельного бэкенда нет: все правила живут в базе, фронт показывает только то, что база и так разрешит.

## Как устроена защита

Всё ниже проверяет база, а не интерфейс. Это покрыто тестами в `tests/db.test.ts`: они ходят в API от имени разных пользователей в обход интерфейса.

- **RLS на всех таблицах.** Аноним не видит ничего. Исполнитель видит свои задачи, объекты, где они есть, и историю этих задач. Чужая задача для него выглядит как несуществующая.
- **Права на колонки.** Клиенту можно записать только название, описание, объект и исполнителя задачи. Статус, автора и дату создания не может записать никто, даже постановщик.
- **Смена статуса — только через функцию `change_task_status`.** Она блокирует строку задачи и проверяет по справочнику `task_transitions`, есть ли такой переход, кто его выполняет (постановщик или назначенный исполнитель) и нужен ли комментарий. Потом пишет историю.
- **История неизменяема.** У клиентов нет прав на запись в `task_history`. Пишут туда только функция смены статуса и триггер правок задачи. Удаляется история только вместе с задачей.
- **Триггеры задачи.** Исполнителем можно назначить только пользователя с ролью «исполнитель». Смена исполнителя сбрасывает статус в «Новая». Правки полей пишутся в историю как «было → стало».
- **Регистрация закрыта.** Пользователей создаёт `scripts/seed.ts` или администратор в панели Supabase. Выдать себе роль постановщика нельзя.
- **Секреты.** Фронт получает только публичный ключ (`sb_publishable_…`). Секретный ключ нужен лишь `scripts/seed.ts --cloud` и берётся из `.env`, который не попадает в репозиторий.

## Структура

```
supabase/migrations/   схема, права, RLS, функция смены статуса, триггеры
scripts/seed.ts        демо-пользователи и данные
src/                   фронт: страницы в src/pages, типы БД в src/database.types.ts
tests/db.test.ts       проверки прав в обход интерфейса (локальный Supabase)
src/*.test.ts          unit-тесты фронта
```

## Локальный запуск

Нужны Node 22+, Docker и [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started).

```bash
npm install
supabase start
cp .env.example .env   # для локального запуска достаточно задать DEMO_PASSWORD
npm run seed
npm run dev
```

`npm run dev` и тесты работают с локальным Supabase: адрес и ключи берутся из `supabase status`, облако не затрагивается.

```bash
npm test             # unit-тесты + проверки прав на локальной базе
npm run typecheck
npm run gen:types    # после изменения схемы: обновить src/database.types.ts
```

## Деплой

1. Облачная база: `supabase link --project-ref <ref>`, затем `supabase db push --remote`.
2. В панели Supabase выключить регистрацию: Authentication → Sign In / Providers → Allow new users to sign up.
3. Заполнить `.env` по `.env.example` и выполнить `npm run seed -- --cloud`.
4. В Vercel задать `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Пуш в `main` собирает и выкладывает фронт.

> **Не выполняйте `supabase config push` из папки проекта.** `supabase/config.toml` — локальная конфигурация из шаблона CLI. Она отличается от облачной примерно в 15 настройках и, например, выключит в облаке MFA и подтверждение email.

Роль постановщика выдаётся SQL-запросом в панели Supabase: `update profiles set role = 'manager' where id = '<id пользователя>';`.
